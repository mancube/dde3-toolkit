Sources (all in `captures/`):

  (137 KB, 653 lines, 323 TX/RX pairs).

## Findings

### UPROG_EIN replies with a 72-byte region/segment descriptor table

> **Superseded / expanded** — see `docs/uprog-ein.md` for the firmware
> decompilation of the `0x0D` handler, the full region-table decode, and what
> the command is used for. It also corrects the "not stored in flash" line
> below (the 72 bytes *are* copied from flash `0x3FC6A`; only bytes 45–47 are
> a runtime value).

Real car: `12 04 0D` → `12 4C A0` + **72 data bytes** (LEN 0x4C = 76 wire
incl. XOR). The payload is `03 FF 60` + 42 × `FF` + a 27-byte tail:

```
03 AE BE 00 7F E4 03 FF 46 03 FF 48 03 7F B0 03 FC B2 03 FF 47 03 FC 4F 03 FF 62
```

- The 72 bytes are **not stored in flash** — not found anywhere in
  `actual_flash.bin`. The firmware assembles the reply.
- The tail's last 24 bytes (`03 FF 46 … 03 FF 62`) **are** a flash window:
  the flash-region table at `0x3FC9A..0x3FCB2` (inside the 0x3FC80 read,
  offset 0x1A), ending right before the AIF slot at `0x3FCB2`.
- The FF padding and the leading `03 AE BE` triple are not a pure flash
  window, so the sim serves the captured 72 bytes verbatim
  (`UPROG_EIN_DATA` in `src/sim.rs`).

### Seed/key

- The seed telegram (reply to `12 08 90 42 4D 57 Z`) is the **ident string
  verbatim** — byte-for-byte identical to the IDENT reply
  (`77868875201124048010281001445G521000000000`, 42 chars). The ident
  string itself is not stored in flash either.
- Z = 0x07 → key `9C A0 97 96` (formula `K[i] = FR[(0x12+i)%46] +
  FR[(Z+i)%46] + FR[(0x29+i)%46]` on the 46-byte wire frame).
- Key-check OK reply is **`12 05 A0 00`** (status + one 0x00 data byte),
  not a bare `12 04 A0`.

### Flash services are session-gated

From the 3-command capture: after UPROG_EIN but **before** seed/key,
FLASH_LESEN gets a **`12 04 A2` NACK stub** (4 bytes, status 0xA2 — not the
generic 0xFF NACK). So the flash services (0x06/0x07) require the full
bootstrap: UPROG_EIN **and** seed/key.

### Flash read sequence

256 × 128-byte FLASH_LESEN, contiguous, `0x038000 → 0x040000` (the
calibration area). First reply data `55 55 00 00 56 …`, last
`FF FF FF FF FF …`. All 256 reply payloads verify against
`actual_flash.bin`.

### AIF

46-byte record at flash `0x3FCB2` (cal `0x7CB2`) — found in the image at
the expected location, served by both 0x02 and the `addr=0 count=46`
FLASH_LESEN path.

### Live loop

42 MW_SELECT_LESEN cycles, single id `0x0F65`: TX `12 07 0B 10 0F 65 64`
→ RX `12 08 A0 10 00 02 51`. Reply-gap p50 ≈ 344 ms → **~2.5 Hz**,
matching the user-confirmed "hard stuck at 2.5 Hz" on the real ECU.

### DTC — known discrepancy, intentionally not fixed

The run shows 4 read cycles (count → entry → shadow, count = 2, entries
`9E F3 9E FD`, shadow `00`) plus 2 clears. **The toolkit's DTC
parse/clear algorithm is wrongly implemented** (per the user) — left
as-is on purpose. The sim's DTC handlers were not touched.

## Fixes applied (`src/sim.rs`)

- `UPROG_EIN_DATA: [u8; 72]` constant (byte-exact from the capture); 0x0D
  now replies `12 4C A0 <72 B>` instead of a bare status.
- `IDENT_DATA: [u8; 42]` constant; the seed telegram is now the ident
  string (was a Z-seeded pseudo pattern), so Z = 0x07 → `9C A0 97 96`
  like the real car.
- Key-check OK now replies `12 05 A0 00` and sets a new `unlocked` latch
  (cleared by DIAGNOSE_ENDE `0x9F`).
- Flash services (0x06 read/erase, 0x07 write) gated on
  `in_prog && unlocked` (`flash_session_open()`); outside the session they
  answer the `12 04 A2` NACK stub (`SB_NACK_FLASH`).
- 0x0A and IDENT already matched the real car (no change).
- DTC handlers untouched (see above).

Tests: new `uprog_ein_and_seed_key_real_car_parity` + `unlock()` helper;
8 existing sim tests updated for the new shapes/gating. `cargo test`:
**92 passed, 0 failed.**

End-to-end: `respond` on a socat pty pair, toolkit `read-cal` against it —
full bootstrap (IDENT → UPROG_EIN `12 4C A0 …` → AIF → seed/key
`9C A0 97 96` → `12 05 A0 00`) then 256 × 128 B reads, 32768 bytes written,
exit 0.
