# Session notes — 2026-11-09 (dual-adapter hardware bring-up)

**Setup decided by user:** `/dev/ttyUSB1` = **sender** (FTDI FT232R,
`usb-FTDI_FT232R_USB_UART_A50285BI`), the toolkit transmits on this adapter.
`/dev/ttyUSB0` = **monitor** (QinHeng 1a86 UART-LPT), passive ECU-side tap.

## 1. Hardware probe (topology confirmed)

Probed both adapters at 9600 8E1:

| Probe | Result |
|---|---|
| FT232 TX → FT232 RX | visible (bus echo — half-duplex K-line) |
| FT232 TX → UART-LPT RX | visible (passive tap sees exactly what the ECU receives) |
| UART-LPT TX → anything | **dead** — the monitor cannot drive the bus |

**Consequence:** an ECU reply physically cannot come from the serial line.
The ECU is therefore simulated **in-process** in the toolkit; the real
frame still goes over the wire and the bus echo is read back to verify the
TX path. The UART-LPT tap is used by `tools/monitor.py` to show the
ECU-side view of every transaction.

## 2. Code changes

### `src/protocol.rs` — reply handling (was broken)

- **Bug fixed:** `request()` previously returned an NRC error for *every*
  reply starting with `0x92` — i.e. every possible ECU response. Now byte
  `[2]` is interpreted as the JOBRESULT status byte when it is a known
  status (`0xA0/0xA1/0xA2/0xB0–0xB2/0xFF/0x00`): OKAY → `Ok(reply)`,
  BUSY (`0xA1`) → resend (max 50), other → NRC. Any other byte at `[2]`
  means a data reply → returned as-is.
- **Reply convention pinned down** from `analysis/frames.md` ("Generic OK
  response fed to each job: `92 04 A0`") and the decompiled FLASH_LESEN
  listing (`decompiled_winkfp.txt` @0xC33C: status read at `S1[2]`, data
  copied from `S1[3]`):
  ```
  <92> <len echo> <SB> [<data ...>]  + trailing XOR on the wire
  ```
- **Flash-read data offset corrected 7 → 3** in `read_full`, `read_range`
  (new shared `check_flash_read_reply` validates `92 … A0` + length).
- Stale parser/pending state cleared per transaction (prevents a leftover
  bus echo being consumed as the next reply).
- Sim hooks: `Kline::set_sim(SimEcu)`, `sim_enabled()`; in sim mode the
  simulated reply is injected after a short pause and `verify_echo()`
  confirms the TX actually reached the bus (logged as `ECHO confirmed`).

### `src/sim.rs` (new) — in-process ECU simulator

- 256 KB flash pre-filled with a deterministic non-zero pattern.
- Services: IDENT (returns `DDE3.0 SIM ECU`), UPROG_EIN (sets prog mode),
  STATUS_CODIER_CHECKSUMME (returns the **real TDI V3.1** application
  checksum of its own flash), DIAGNOSE_ENDE, SEED_KEY (`12 08 90 42 4D 57
  05 Z`), FLASH_LESEN `12 09 06 A A A n`, FLASH_LOESCHEN `12 09 07 06 …`
  (count 0 = erase to end of image), FLASH_SCHREIBEN `12 09 07 02 …`
  (**gated on programming mode**), FLASH_SCHREIBEN_ENDE,
  DATENBEREICH_LOESCHEN_0E (fault clear), MW_SELECT_LESEN `12 05 0B 10 …`
  (deterministic big-endian u16 values, reply `92 05 0B 10 A0 <vals>` to
  match `Kline::live_values`). Unknown → NACK `92 … FF`.
- Note: for the `12 09 07 <sub>` family the address sits at p[4..7]
  (sub-code at p[3]) — one byte right of FLASH_LESEN; this tripped the
  first unit tests.
- 4 new unit tests.

### `src/main.rs`

- Default port `/dev/ttyUSB0` → **`/dev/ttyUSB1`** (FT232 sender).
- New `--sim` flag on all wire commands (ident, read, read-cal, write,
  write-cal, seed-key, fault-clear, uprog-ein, diagnose-ende).
- `read`/`read-cal` reply parsing fixed to the `92 … A0 <data@3>` layout.
- `write`/`write-cal` in sim mode now **read the image back after writing
  and byte-compare** (mismatch → error with first bad offset).

### `tools/monitor.py` (new) — passive ECU-side tap viewer

- Runs on `/dev/ttyUSB0`, 9600 8E1; frames the traffic (payload + trailing
  XOR), greedily extracts complete frames from multi-frame reads, verifies
  XOR, names the DDE3 service. Two bugs found and fixed during the session
  (service keys were swapped sid/sub; back-to-back frames merged into one
  "frame" because only the blob tail was validated).

## 6. Live wake comparison on the tap (2026-11-09 ~22:18)

Sniffer: `EDC15C4-decomp/analysis_artifacts/tools/kline_sniff.py` on
`/dev/ttyUSB0` (passive ECU-side tap, 9600 8E1), capturing only the
tester→ECU direction. Captures archived as
`analysis/captures/wake_comparison_2026-11-09.{raw,framed.log}`.

User sent the **DDE4 toolkit wake** first, then the **DDE3 toolkit wake**.

| | DDE4 wake | DDE3 wake |
|---|---|---|
| Telegram | `B8 12 F1 01 A2 F8` | `12 04 00 16` |
| Framing | BMW KWP2000* mode 11: `B8 <tgt> <src> <len> <payload> <xor>` | bare DDE3: `12 <len> <sid> [<sub>] ... <xor>` |
| Service | `A2` = IDENT (KWP) | sid `0x00` = IDENT (DDE3) |
| Checksum | XOR over `B8 12 F1 01 A2` = `F8` ✓ | XOR over `12 04 00` = `16` ✓ |
| Attempts | 5, ~1.25 s apart | 4, ~1.2 s apart |

Findings:
- The wake telegrams share **no bytes in common** except the target address
  `12`. The DDE4 KWP envelope (`B8`/`F1`/`A2`) is entirely absent from the
  DDE3 traffic — confirms the dde3 toolkit must not inherit DDE4 framing.
- Retry cadence is similar in both toolkits (~1.2–1.25 s), so timing logic
  is shared conceptually; the difference is framing/services only.
- No E→T reply visible in either phase (tap limitation, known since §1).
- The sniffer's DDE4-only parser framed the DDE4 wake cleanly (5 `T->E`
  frames) and emitted only RAW for the DDE3 frames — exactly the expected
  asymmetry.

## 7. Remake-audit: dde3-toolkit vs dde4-toolkit (same day)

Question: was dde3-toolkit correctly re-derived from dde4-toolkit with the
framing difference (see §6) in mind?

| Aspect | dde4-toolkit (reference) | dde3-toolkit (verified) | Verdict |
|---|---|---|---|
| Frame builder | `B8 12 F1 LEN <payload> <xor>` (`FMT=0xB8`, `TESTER_ADDR=0xF1`) | `<payload> <xor>` only — no B8, no F1, no LEN | ✓ diverged as it must |
| IDENT wake | `[0xA2]` → `B8 12 F1 01 A2 F8` (unit-test asserted) | `[0x12,0x04,0x00]` → `12 04 00 16` (unit-test asserted) | ✓ both byte-exact vs today's capture |
| Positive reply style | KWP: reply SID = `sid \| 0x40` (e.g. `E2`) | DS2: first byte `92` = `ECU_ADDR \| 0x80`, status byte at [2] | ✓ no `\| 0x40` logic in dde3 src |
| KWP services (2C/21/23/1A/3E/81/82/83/A2-as-SID) | present | absent (only `0xA2` appears as a JOBRESULT *status* byte, a different namespace) | ✓ clean |
| Flash-read addressing | `23` BE: `addr>>16, addr>>8, addr` | `12 09 06` LE: `addr, addr>>8, addr>>16` | ✓ per-protocol |
| Reply data offset | — | `92 <len> <SB> <data@3>`, status A0/… per decompiled listing | ✓ matches decomp |
| Timing | 9600 8E1 | 9600 8E1 | ✓ shared (correct — same physical layer) |

Checks executed:
- `cargo test` in dde3-toolkit: **16/16 pass**, incl. `captured_winkfp_frames`
  asserting byte-exact `12 04 00 16` (today's captured DDE3 wake) and the
  parser splitting/echo behavior.
- `grep` for DDE4 constants (`0xB8/0xF1/0xA2-as-SID/0x2C/0x23/0x21/0x1A/0x3E/0x81-83`)
  over `dde3-toolkit/src`: only legitimate hits (doc note, JOBRESULT status
  `0xA2`, checksum offsets `0xB80/0x40000`).

Conclusion: the remake is correctly DDE3-shaped; the observed wake difference
(§6) is exactly what the two codebases emit. Retry cadence in both toolkits
is user-driven repeats (each `ident` is one request, ~0.5 s timeout), not a
built-in wake loop.
